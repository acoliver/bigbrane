# Start Bigbrane's research loop from RD-Agent, with a separate trusted evaluator

**Microsoft RD-Agent is the better starting foundation for Bigbrane's hypothesis, design, code, experiment, and analysis loop.** Its source already represents hypotheses, experiments, feedback, trace ancestry, checkpoint selection, and repeated development. DeerFlow offers more developed general-agent delegation, recovery, and evidence plumbing, but Bigbrane would have to supply the scientific search policy and experiment state machine. [R1-R7, D1-D6]

Use RD-Agent's research interfaces and loop machinery selectively. Its default data-science application optimizes competition scores and contains assumptions about ensembles, `main.py`, and `scores.csv`. Turning that application into a mathematical-discovery system requires scenario, proposal, execution, and feedback adapters. A custom dataset description alone would leave those assumptions in place. [R4-R8]

**Do not adopt either default execution path as Bigbrane's confirmation boundary.** RD-Agent's custom-dataset format validator copies reference answers into the writable experiment workspace, and its final grader executes there. DeerFlow's acceptance checks establish limited file and recorded-command evidence; durable batch acceptance is advisory. Both require an independently controlled evaluation service before agent-written candidates can support confirmatory claims. [R9, D5-D6]

This recommendation concerns the research core, rather than which product has the broader interface or deployment options. DeerFlow is the preferred alternative if the immediate objective changes to an interactive workbench for delegated research with recovery. There is no measured head-to-head result for this workload.

### What the foundation needs to do

Bigbrane's objective is to investigate mathematical learning mechanisms that use fewer examples, fewer parameters, or subquadratic resources at comparable quality. It needs to turn observations into falsifiable hypotheses, design controlled experiments, implement candidate mechanisms, execute them, and retain both favorable and unfavorable findings. A theory claim also needs assumptions and an argument or proof obligation; an improved validation score cannot establish an asymptotic or sample-complexity theorem.

The existing instrument already has exact next-token oracles, HMM/RNN/attention controls, validation-only checkpoint selection, frozen confirmation, generator-level comparison, descriptive bootstrap intervals, and source/data/environment inventories. The completed first study used 576 candidate fits. It supported low-data HMM KL advantage but established earlier sustained target crossing against both controls on only 1 of 8 generators. Its stress advantage failed against both controls jointly. Those observations motivate new experiments; they do not justify modifying the completed protocol.

The platform should preserve this instrument and result. Exploration needs new data and protocol versions, followed by a separately frozen confirmation lane. Exact-oracle diagnostics may guide exploration on disclosed development generators, but the confirmation generators, oracle parameters, and results must remain outside the agent's authority until the chosen claim and procedure are frozen.

## RD-Agent: research abstractions, with applied-ML assumptions to remove

### 1. Interfaces and actual workflow

`rdagent/core/scenario.py` defines `Scenario` with background, data description, presentation, combined scenario description, runtime environment, and optional experiment settings. Its comments explicitly separate scenario information from a particular method's configuration. `rdagent/core/proposal.py` supplies `Hypothesis`, `ExperimentFeedback`, `HypothesisFeedback`, `Trace`, `CheckpointSelector`, `SOTAexpSelector`, `ExpPlanner`, `ExpGen`, `HypothesisGen`, `Hypothesis2Experiment`, and `Experiment2Feedback`. These are useful seams for a new sequence-learning research domain. [R1-R2]

Representative existing contracts, abbreviated to omit constructors and generic parameters:

```python
class Scenario:
    def get_source_data_desc(self, task: Task | None = None) -> str: ...
    def get_scenario_all_desc(
        self, task: Task | None = None,
        filtered_tag: str | None = None,
        simple_background: bool | None = None,
    ) -> str: ...
    def get_runtime_environment(self) -> str: ...

class ExpGen:
    def gen(self, trace: Trace) -> Experiment: ...
    async def async_gen(self, trace: Trace, loop: LoopBase) -> Experiment: ...

class Hypothesis2Experiment:
    def convert(self, hypothesis: Hypothesis, trace: Trace) -> Experiment: ...

class Experiment2Feedback:
    def generate_feedback(
        self, exp: Experiment, trace: Trace,
        exception: Exception | None = None,
    ) -> ExperimentFeedback: ...
```

`Developer.develop` is the coding/execution seam. Its documentation expects experiment mutation to preserve intermediate work on exceptions. The base `Feedback` concept distinguishes acceptable from finished, but both default methods defer to boolean truth, whose base implementation returns true. The Bigbrane adapter must define these meanings explicitly, rather than inherit a permissive default. [R3]

`RDLoop` constructs scenario, hypothesis generator/converter, coder, runner, and summarizer using configurable dotted class names. Its stages are `direct_exp_gen`, `coding`, `running`, `feedback`, and `record`. However, it imports Qlib utilities and initializes a plan with `ALPHA20` finance features. This is a concrete domain dependency inside the nominal general loop. Prefer a small `LoopBase` composition using the research contracts, or a carefully scoped override of that initialization, over importing the full DS application and pretending the domain boundary is already complete. [R4]

`DataScienceRDLoop` supplies a working specialization. It directly instantiates data-loader, feature, model, ensemble, workflow, and pipeline coders, chooses configured experiment generators/selectors, and records coder/runner errors as rejected feedback. Unsupported task components raise `NotImplementedError`. Its DS defaults select a Kaggle scenario, `ParallelMultiTraceExpGen`, `RoundRobinScheduler`, and `DSExperiment2Feedback`, with one trace by default. Whole-pipeline coding and specification are enabled; knowledge base, research RAG, hypothesis critique/rewrite, planner, model dumping, and several other features are disabled by default. [R5-R6]

The custom-dataset documentation gives a smaller entry point: competition data and `description.md`, plus a separate `eval/<competition>/` containing reference submissions, `valid.py`, and `grade.py`. The inspected example grades AUROC and emits JSON. That demonstrates a scalar metric adapter, not arbitrary research-policy integration. `DSRunnerEvaluator` expects model/ensemble rows and a metric column in `scores.csv`; `DSCoSTEERRunner` reads that CSV into `exp.result` and performs direction-aware score replacement. Bigbrane's KL curves, parameter counts, quality matching, exposures, and scaling diagnostics need their own structured result schema. [R7-R8]

### 2. Hypothesis generation, literature, history, and selection

The DS proposal implementation uses scenario descriptions, previous experiments/feedback, current best code, identified problems, and sibling hypotheses to propose changes. `HypothesisDetail` includes challenge, hypothesis, expected impact, component, and model-generated alignment/impact/novelty/feasibility/risk scores. Its component vocabulary and improvement framing target a data-science pipeline. They need expansion for state representations, learning rules, identifiability assumptions, derivations, complexity claims, and discriminating experiments. LLM novelty scores provide search guidance, with no independent novelty evidence established by this mechanism. [R10]

Optional research RAG is connected to hypothesis generation. The code describes retrieval from community discussions and public code. Its RAG agent attaches `MCPServerStreamableHTTP`, defaulting to `http://localhost:8124/mcp` with a 120-second timeout. The configuration contains a TODO about how to run that server. This is an extension seam requiring an actual service, rather than a supplied complete scholarly literature system. Literature ingestion, primary-source access records, contradictory results, and citation checking remain adapter responsibilities. [R10-R11]

`Trace.hist` stores experiments with feedback, and `dag_parent` stores ancestry. Its documentation says multiple-parent relationships are not implemented. `DSTrace` tracks uncommitted experiments, siblings, roots/leaves, selected best experiments, and retrieval of successful and failed histories. Round-robin, length-based, score-based, random, and simplified PUCT-like MCTS schedulers are implemented. MCTS normally rewards the feedback decision as 1 or 0; the optional score reward uses the ensemble metric and direction. These are experiment-search decisions, not statistical acceptance rules. [R2, R12]

Failures remain useful inputs to development and proposal generation. A negative empirical hypothesis result needs a richer state than “do not replace best”: preserve numerical outcomes and validity separately from search promotion. Consecutive drafting failures can reset the active trace, while logging the previous trace. Retain that earlier attempt ledger outside active search state so the denominator cannot disappear during resets. [R5, R12]

### 3. Execution, limits, and recovery

Execution is real Python or shell code, rather than a report-only workflow. `FBWorkspace.run` injects workspace files and invokes an `Env`. The DS environment factory defaults to Docker and also offers Conda-backed `LocalEnv`; the latter runs on the host and supplies no container boundary. `Env.run` wraps entries in GNU `timeout --kill-after=10` when a limit is configured. DS debug/full limits default to 600/3,600 seconds, coder development to ten loops, and runner refinement to three loops. These are configurable controls. [R6, R13-R14]

`DockerConf` defaults to a writable workspace, read-only extra mounts, bridge networking, GPU probing enabled, a 48 GB memory limit, no CPU-count limit, and five retries after exceptions. A nonzero executed-command return is returned as a result, not automatically retried by that exception loop. The implementation logs container identity, environment and mounts, waits for the exit code, and cleans up the container in `finally`. CPU quota semantics need runtime validation on a Linux daemon; a `cpu_count` field should not be treated as measured one-thread compliance. [R14]

`LoopBase` has per-step semaphores, parallel kickoff/execution, loop and step counts, and an overall-duration timer. It saves a snapshot after a step advances. Loading can recover the latest snapshot or a selected stage, and checkout can use a new folder. The DS CLI accepts a session path and passes loop/step/duration controls. The default CLI checkout behavior can truncate later session logs, so research continuation should explicitly preserve them or checkout into a new path. Interrupted unfinished steps can rerun; candidate execution must have idempotent attempt IDs and independent training checkpoints. No exactly-once recovery guarantee follows from the snapshots. [R15-R16]

Snapshots use HMAC-SHA256 signed pickle envelopes. Unsigned legacy pickle is rejected by default, and tests explicitly exercise rejection before deserialization. The signing key is configured or created under `~/.rdagent` with restrictive permissions. Keep it outside agent mounts. Signature verification establishes that the bytes came from a key holder; pickle still requires trusted authorship and access control. It does not independently attest scientific correctness. [R17]

Workspace checkpoint comments refer to a 100 KB file cutoff, but the actual `workspace_ckp_size_limit` default is **0, meaning no limit**. The code uses that configurable value and can include regular files of any size under the default. Symlinks are archived separately. Thus, asserting a default 100 KB truncation would be wrong at this commit. Separately, the optional DS log-archive path calls `clean_workspace`, which deletes subdirectories and files outside `.py`, `.md`, and `.csv`; `.pt`, `.npz`, JSON manifests, and nested raw artifacts would be at risk. Keep this archive path off for Bigbrane and export immutable artifacts independently. [R18, R5]
Additional execution boundaries need attention. The inspected Docker launch does not set capability drops, no-new-privileges, or a PID cap, and its command wrapper recursively applies `chmod 777` to workspace contents outside configured exclusions. The dataset scenario can also execute dataset-supplied `sample.py` directly through host `runpy.run_path` when LLM sampling is disabled. Treat supplied dataset scripts as executable inputs; route them into isolated execution rather than trust a data-directory label. These findings concern the inspected paths and do not constitute a demonstrated exploit. [R14, R27]


### 4. Evaluator authority and scientific validity

The current custom-dataset evaluator provides **insufficient isolation for Bigbrane confirmation**. `TestEval.valid` injects both `submission_format_valid.py` and `submission_test.csv` into the writable workspace, executes the validator there, then removes those files. `DSRunnerEvaluator` calls this format check during development when reference evaluation is enabled. `TestEval.eval` likewise injects `grade.py` and the answer CSV, then executes the grader in the same workspace. The example validator only needs the reference row count, yet receives the full reference file. [R9, R8]

This source establishes a reference-answer exposure window and mutable execution context. It does not establish that an observed agent exploited them. Cleanup afterward cannot retroactively protect data from candidate code or background processes. Read-only input mounts prevent edits to those mounts, while still allowing reads. They do not solve the answer exposure or grant an independent grader authority.

Training-side `scores.csv` originates from candidate code. The evaluator checks expected rows/columns and execution output, but an LLM contributes acceptability and tuning feedback. `DSExperiment2Feedback` compares scores, code diff, history and EDA, then asks an LLM for replacement/acceptability decisions; detected task/evaluation misalignment can force rejection. These checks help ordinary engineering. They do not independently recompute metrics from raw predictions or freeze scientific hypotheses and thresholds. [R8, R19]

No preregistration policy, generator-level paired confidence procedure, multiplicity control, or protected exploration-to-confirmation transition was found in the inspected workflow, scenario, proposal, runner, feedback, and evaluation files. This is a finding about those files, not a claim that no such policy exists anywhere in RD-Agent. The DS documentation explicitly describes optimizing validation/leaderboard performance and uses “test set” in its iterative workflow. The adapter must define which feedback is reusable development information and which is final confirmation. [R7]

### 5. Models, tool APIs, and cost accounting

The default `LLMSettings.backend` is `LiteLLMAPIBackend`. LiteLLM handles provider-specific model strings; installation documentation supplies OpenAI-compatible endpoint and embedding examples. `get_complete_kwargs` applies `chat_model_map` entries based on the logger's active tag, permitting different researcher/developer models and sampling settings. Routing is tag-based and first-match, so overlapping tags and changes to logging scope need contract tests. Chat and embedding model choices are separate. [R20-R21]

OpenAI, Anthropic through LiteLLM's provider routing, and compatible local endpoints are feasible for the ordinary completion path, subject to dependency/provider support. The optional RAG/tool-agent path is narrower: `get_agent_model` builds a Pydantic-AI `OpenAIChatModel`, asserts a LiteLLM backend, and allows only `openai`, `azure_ai`, `azure`, and `litellm_proxy` provider mappings. A direct Anthropic provider setting does **not** satisfy that bridge. Use a tested proxy-compatible path or implement the required provider adaptation before enabling research RAG. Local JSON/schema and tool-call capabilities are also acceptance-test requirements. [R22]

`APIBackend` has configurable retries, cache handling, schema/JSON processing, and continuation behavior. LiteLLM completion is called with `max_retries=0`, with framework retries at the surrounding layer. Defaults include ten framework retries and a one-second retry wait. Some inherited LLM settings are marked as belonging mainly to the deprecated backend, so a setting's presence alone does not demonstrate that it controls the current LiteLLM transport. [R20-R21]

The backend logs estimated prompt/completion tokens, per-call cost, and a process-global `ACC_COST`. Failed price lookup becomes NaN; failed token counting becomes zero with a warning. This cannot supply a complete bill or durable cross-process study budget. No monetary admission/stop was found in the inspected backend and loop paths. Loop counts, response token limits, execution deadlines, and total duration bound different resources. Add a trusted study ledger that counts retries, failures, literature calls, embeddings, and confirmation separately.

## DeerFlow: execution workbench with scientific policy still to build

### 1. Embedding, tools, models, and extension APIs

The direct Python factory is a usable entry point without the Gateway or frontend:

```python
create_deerflow_agent(
    model: BaseChatModel,
    tools: list[BaseTool] | None = None,
    *,
    system_prompt: str | None = None,
    features: RuntimeFeatures | None = None,
    state_schema: type | None = None,
    checkpointer: BaseCheckpointSaver | None = None,
    subagent_runtime: SubagentRuntime | None = None,
    # Additional middleware, checkpoint, and policy arguments are supported.
) -> CompiledStateGraph
```

It accepts supplied tools and state, assembles feature middleware, and passes the checkpointer to LangChain's agent graph. A full `middleware=` takeover bypasses feature assembly; do not assume default controls survive such a takeover. Persisted delta-state mode is rejected in this direct factory because it bypasses the guarded checkpoint-mode path. Use full state for a minimal embedded adapter. [D1]

`SubagentConfig` specifies description/system prompt, tool allow/deny lists, skills, selected model, turns, and timeout. The bare dataclass defaults to 50 turns and 900 seconds; builtin/global application configuration can increase these, including the documented 1,800-second builtin timeout. Recursive `task` delegation is denied by the bare default. The model can be explicitly selected per subagent or inherited from the parent. [D2]

`create_chat_model` resolves a configured `BaseChatModel` class, normalizes compatible endpoint parameters, applies sampling overrides, enables streaming usage where supported, and attaches tracing. Configuration examples show `ChatOpenAI`, `ChatAnthropic`, optional native `ChatOllama`, and local OpenAI-compatible URLs. OpenAI-compatible stream chunk gaps default to 240 seconds; retry/admission behavior also depends on the configured client and error-handling middleware. A lead-agent request for an unknown model can fall back to the first configured model, whereas direct factory model lookup raises. The adapter should record the actual resolved model and reject unapproved substitutions. [D8]

The inspected `LLMErrorHandlingMiddleware` declares a three-attempt ceiling, uses reason/exception-specific smaller budgets, and applies retry backoff/jitter. Application configuration can override that ceiling. This controls individual model calls; it does not retry a complete scientific experiment or reconcile duplicate external tool effects. Subagent execution additionally has an overall timeout and structured timed-out/cancelled/failed status. [D19, D2]

The extension contract exposes middleware contributions, task start/stop hooks, system-model-call observers, runtime services, and eagerly registered HTTP routers. The bundled example counts tool calls, aggregates task outcomes, observes auxiliary model calls, and exposes stats through a service/router. It demonstrates where to attach an experiment ledger and budget observations. It does not implement hypothesis selection, statistical evaluation, or autonomous theory discovery. Custom tools can call a trusted experiment service; a full UI plugin is optional. [D9]

### 2. Durable delegation and scheduling

`SubagentRuntime` can own native-subagent execution capacity and a SQL-backed `SubagentBatchService`. The explicit runtime must be started before graph assembly; its owned batch service supplies batch tools. Batch configuration is **disabled by default**, with three attempts, three concurrent running items by default, bounded live-item/item/result sizes, and 120-second leases when enabled. [D3-D4]

The SQL repository persists submissions, items, attempts, status and results, recovers expired leases, and handles pause/resume/cancel/retry. Submission-key handling supports duplicate submission recovery. The service renews leases while execution or acceptance checks proceed, avoids launch after lease loss during tool assembly, and requeues capacity-admission failures without consuming an execution attempt. Shutdown leaves unfinished work recoverable after lease expiry. [D3-D4]

The worker passes a stable item key in the prompt to encourage idempotent side effects. That instruction alone does not enforce idempotency. The subagent executor assembles its graph with `checkpointer=False`, so durable batch recovery should be understood as persisted item orchestration and retry, rather than automatic instruction-by-instruction continuation of that worker's conversation. Bigbrane's candidate checkpoints should remain the source of fit resumption. [D2-D4]

The inspected REST router provides thread-owned batch listing/status/items, pause/resume/cancel, item retry, and JSONL result export under `/api/threads/{thread_id}/subagent-batches`. It does not expose a batch creation endpoint in that router; use the tool/service submission seam rather than inventing a REST call. `ScheduledTaskService` separately implements queued scheduled/manual dispatch, occurrence ownership, leases, finalization and stale-run reconciliation. Calendar scheduling coordinates runs; it supplies no hypothesis-search policy. [D10]

Graph persistence supports memory, SQLite and PostgreSQL. The separate checkpointer configuration defaults to memory; the unified application database configuration defaults to SQLite when omitted. These are different construction paths. Memory loses state on restart. Application multi-instance mode requires PostgreSQL, DB events, heartbeats and a Redis stream bridge, with additional startup constraints. Start with an explicit single-process persistent configuration rather than claim that every embedded graph is durable by default. [D11]

### 3. Receipts, verification, and authority

Tool receipts record call identity, tool name, status, argument/output hash summaries, output byte count and timestamp. They are runtime-stamped into message metadata and surfaced as citations. The source explicitly distinguishes execution evidence from task acceptance, and warns that receipt freshness and message retention matter. These hash summaries are not a replacement for Bigbrane's complete file inventories and immutable content digests. [D5]

Deterministic acceptance supports scoped file existence/nonempty checks, bounded JSON syntax checks, file-written evidence, and `tests_passed:<command>` bound to a matching recorded bash execution and a test-summary-shaped output. JSON checking rejects nonfinite values but provides no scientific schema or semantic validity. The checker declines uncertain cases as UNVERIFIED, including persistent-shell command evidence whose earlier state cannot be shown clean. Full parent-side command re-execution is deferred in the inspected module. A runtime record that tests ran successfully cannot establish that candidate-controlled tests or results are trustworthy. [D6]

For durable batches, checker errors leave results unchecked; a completed executor can still finalize as `succeeded` regardless of the advisory acceptance verdict. Therefore `succeeded` must not promote a Bigbrane hypothesis. A trusted service must independently validate candidate interfaces, recompute metrics, enforce the protocol, and choose confirmation status. [D3, D6]

No scientific evaluator-protection or preregistration policy was found in the inspected embedding, delegation, receipt, acceptance, configuration, and deep-research skill files. This statement is limited to those sources. Role prompts, tool filters, sandbox isolation, and protected metric authority address different boundaries; none should be substituted for another.

### 4. Executable sandbox and host security

The examined example configuration defaults to `LocalSandboxProvider` with **`allow_host_bash: false`**. It explicitly says host shell access is unsuitable as a secure isolation boundary. The local implementation includes file-path/mount checks and tool-level read-only enforcement, but host execution, when deliberately enabled, remains host execution. Its shell implementation uses a new POSIX process session and process-group termination for foreground timeouts. Default command timeout is 600 seconds. Background processes are a separate lifecycle concern. [D12]

Container AIO execution is an alternative that must be configured. Its local backend detects Apple Container on macOS for open networking, otherwise Docker; restricted network modes require Docker. Docker execution drops capabilities except an image-startup compatibility set, sets no-new-privileges, and defaults to 2 GB memory, two CPUs and 512 PIDs. It does **not** force a non-root user; supported images need ownership/user transitions. Default seccomp is unconfined for the shipped browser path, with configuration to use a tested restricted profile. Open networking is the default, and the source explicitly notes access to internal networks/metadata endpoints without dedicated egress policy. These qualifications matter when describing the sandbox. [D13]

The default Compose file does not mount the host Docker socket. An explicit Docker-outside-Docker overlay adds it to the trusted Gateway. That socket gives broad daemon authority and must never be exposed to candidate code. Mount only development inputs and one writable candidate directory into execution containers. Keep evaluator files, confirmation data, signing secrets, LLM keys, and artifact inventories in another authority domain. [D14]

Documentation and code distinguish server-side command deadlines from client request timeouts for different AIO image lines. The frozen legacy `:latest` image does not receive the same server-side `hard_timeout` behavior as supported semver images. Pin a tested image digest and verify that deadline expiry actually kills the workload. Do not infer isolation or cancellation from a provider name alone. [D12-D13]

### 5. Research, history, statistics, and negative results

DeerFlow can use research skills, search/fetch tools, local documents, memory, role-specific subagents, and external MCP services. Its inspected `deep-research/SKILL.md` is a procedural prompt for broad search, focused reading, diverse evidence and synthesis. That file supplies no executable hypothesis tree, theorem checker, experiment planner, or significance procedure. Literature/source quality remains a workflow contract. [D15]

Thread history, memory, artifacts, batch results, and traces can support research records. They do not encode experiment ancestry and scientific status automatically. Bigbrane would need an explicit state machine and ledger linking hypothesis, protocol, candidate revision, data seeds, run attempts, metrics, interpretation and selection. A failed or inconclusive hypothesis must be retained even if no delegated task failed. The application would also need to separate historical exploratory feedback from sealed confirmation outputs.

No paired-bootstrap or equivalent comparison policy was found in the inspected receipt/acceptance/batch and research-skill paths. Use Bigbrane's statistics through a trusted tool. A skill that tells an agent to be systematic does not enforce replication units, frozen decisions, or fair resource accounting.

### 6. Tokens, dollars, and auxiliary calls

Lead token budgeting is disabled by default. Its configurable cap defaults to 200,000 total input/output tokens when enabled. Native subagents have enabled default backstops of 2,000,000 tokens without summarization or 1,000,000 with summarization, unless overridden. Concurrency/delegation limits bound another dimension. [D16]

`TokenBudgetMiddleware` accounts usage metadata after model responses, includes retroactive subagent usage on parent messages, and shares a budget across continuations with the same run ID. It strips tool calls and surfaces `token_capped` after crossing the threshold. Consequently it can overshoot by an already completed call or concurrent child work. Later user runs receive fresh budgets, and absent usage metadata cannot produce complete accounting. Durable batch tokens are stored per result, but no study-wide shared batch dollar admission mechanism was established in these inspected paths. [D16]

Per-model pricing and tracing provide reporting inputs, with configuration caveats for mixed currencies. System-call observer hooks cover goal, memory, title and summarization calls, which helps an adapter account for work outside ordinary tool/model middleware. Neither those hooks nor token caps alone supply a hard project-dollar ceiling. Use reservations before external calls plus reconciled actual usage, and mark unreported usage as unknown rather than zero. [D9, D16]

## Runtime, dependencies, macOS deployment, and licenses

### RD-Agent

**Documented support is Linux only.** The README says this explicitly and requires Docker for most scenarios, despite the package classifier saying OS Independent. Packaging requires Python >=3.10, with 3.10/3.11 CI. Dependencies include OpenAI/LiteLLM, Pydantic-AI, Docker, NumPy/Pandas/scikit-learn, PDF tooling, Selenium/Kaggle, Streamlit/Flask, MLflow/Azure integrations, and Prefect. It is a broad application environment; placing all of it in Bigbrane's existing numerical virtualenv would couple unrelated dependencies. Keep environments separate. [R23]

The inspected DS image starts from `gcr.io/kaggle-gpu-images/python:latest`, and another scenario image explicitly uses `pytorch/pytorch:2.2.1-cuda12.1-cudnn8-runtime`. The single-container recipe uses mutable/latest bases, unpinned repository clones and externally fetched provider setup. These recipes establish Linux/NVIDIA-oriented deployment assumptions, not reproducible CPU execution for Bigbrane. They were read, never built or executed. This report did not inspect image manifests and therefore does not assert a particular image is amd64-only or that arm64 is available. [R24]

GNU `timeout`, POSIX shell paths, shared `/tmp/sample` or `/tmp/full` caches, and a Docker build helper's literal Unix socket reference make native Darwin execution a poor first integration. Shared caches also need per-study namespacing. CUDA/NVIDIA probing cannot use this machine's Apple GPU, but `enable_gpu=False` can deliberately select CPU execution. Fixed container paths such as `/kaggle/workspace` are configurable mount choices, not proof of unavoidable x86 code. [R14]

Recommended untested architecture: run the RD-Agent controller and candidate executor in a dedicated Linux environment, using a purpose-built CPU image containing only the declared numerical dependencies and necessary runtime tools. On this Apple Silicon host, first test an arm64 Linux VM/image; use a separate Linux x86 host only if required dependencies/images prevent that route. A container cannot use native macOS MPS through Docker. Call a trusted evaluation service under a separate account/container with confirmation data never mounted into candidate execution. The already usable native Bigbrane harness can remain the authoritative evaluation lane, but its native timing results and Linux exploration timings must be labeled separately. Native macOS controller execution would be a port beyond advertised support, not a supported default.

### DeerFlow

The Python backend/harness requires >=3.12 and uses LangChain/LangGraph, SQLAlchemy/Alembic, SQLite, model/search integrations, sandbox SDKs and document conversion. Optional extras include PostgreSQL, Redis, Ollama, browser, and several sandbox providers. The full application adds FastAPI and channel dependencies; its frontend is TypeScript/Next.js 16, React 19 and pnpm 10.26.2. Backend Docker uses Python 3.12 slim Debian and a Node 22 build/runtime path. Bigbrane can embed the Python harness without adopting that frontend or all Gateway services, although the harness dependency set remains broad. [D7, D14]

The source includes macOS runtime detection, so a blanket Linux-only claim would be false for DeerFlow. An isolated Docker VM is the more suitable first execution route here because Docker supports the inspected restricted-network and resource/security controls, while Apple Container mode does not receive those Docker-only flags. Native-host harness plus controlled Docker workers avoids mounting the host socket into a general application container. Alternatively use the full Compose stack with the explicit socket overlay restricted to trusted control services. Neither route was exercised here. No AIO image architecture manifest was inspected, so arm64 availability remains a deployment acceptance test. [D13-D14]

Local model endpoints must be reachable from the component making the LLM call. A Docker-hosted controller's `localhost` names the container; the examples show `host.docker.internal` for host inference services. Pin and test tool calling, JSON/schema behavior, token metadata and actual resolved model identity. Successful connection alone does not establish model suitability. [D8]

## Recommended integration contracts

These are proposed adapter contracts, not additions to the existing harness. Start with a narrow research brief, such as diagnosing HMM optimization adequacy or testing an unknown-state representation, on new development data. Keep Experiment 1 immutable.

A framework-independent service boundary should carry explicit authority:

```python
class ResearchExecutor(Protocol):
    def run_development(
        self, candidate_digest: str, protocol_digest: str,
        attempt_id: str,
    ) -> DevelopmentReceipt: ...

class ConfirmationAuthority(Protocol):
    def freeze(
        self, candidate_digest: str, protocol_digest: str,
        selection_ledger_digest: str,
    ) -> FrozenStudyHandle: ...
    def confirm(self, frozen: FrozenStudyHandle) -> ConfirmationReceipt: ...
```

The actual schema should include hypothesis and parent IDs, mechanism and assumptions, predicted effect and falsifier, proof obligations where relevant, dataset/generator identities, candidate/source/environment hashes, seeds, raw metric locations, parameter/resource conventions, all attempt IDs, failures, unknown costs, and selection reasons. Development receipts disclose only permitted development results. A confirmation capability is unavailable to ordinary agent tools; an external policy transition grants it after freeze. Protocol changes invalidate a pending freeze instead of silently mutating it.

Validity, scientific support, and search ranking must be independent fields. A numerically correct run can reject a hypothesis. An invalid run supplies debugging feedback and no scientific result. A budget-exhausted or inconclusive run remains in the ledger. A high-ranked exploratory candidate still has no confirmatory status.

### Adapter A: RD-Agent scientific scenario, recommended

Use approximately **six to eight cohesive adapter modules**, plus the protected execution/evaluation boundary and its tests. This is a proposed design magnitude, not a measured implementation estimate.

1. **Scenario:** implement `BigbraneScenario(Scenario)` with development-data descriptions, assumptions, runtime description, and protocol constraints. Keep oracle/confirmation secrets out of scenario text and workspace state.
2. **Proposal and design:** implement `BigbraneExpGen(ExpGen)` or the separate `HypothesisGen`/`Hypothesis2Experiment` seams. Generate explicit mechanism, assumptions, expected data/parameter/resource changes, ablations, and falsification criteria. Replace DS component and ensemble-improvement prompts. Feed literature through an archived source packet first; optional MCP retrieval can be enabled after provider/service tests.
3. **Candidate development:** a `Developer` adapter writes only approved candidate modules. The existing fixed harness does not automatically accept arbitrary new model families: define a candidate prediction/training contract or a separate follow-on harness adapter, rather than allow the agent to edit the evaluator to fit its candidate.
4. **Execution:** implement a runner `Developer` that submits candidate/protocol digests and stable attempt IDs to `ResearchExecutor`. Disable candidate-authored score authority, DS `TestEval`, workspace answer injection, archive cleaning, automatic timeout increases, and uncontrolled reruns. Preserve Bigbrane's fit checkpoints and independent resource measurements.
5. **Feedback:** implement `Experiment2Feedback` with deterministic validity/support decisions from trusted receipts and an LLM interpretation field. A negative result stays available to subsequent hypothesis generation. Selection uses a declared multi-metric or constrained objective, not an ensemble CSV scalar chosen by the agent.
6. **Loop/history:** compose `LoopBase` stages with `Trace` and explicit selectors, avoiding Qlib plan initialization and hardcoded DS coders. Restrict the first trial to one trace and fixed candidate/fit caps; add branching only after attempt identity and full-denominator retention pass tests.
7. **Provenance/budgets:** persist every hypothesis, revision, retry, receipt and selection outside candidate storage. Restore signed snapshots with a private signing key; preserve previous logs through new checkout paths. Enforce experiment-wide resource/spend admission independently of framework logging.
8. **Confirmation transition:** freeze protocol, selected candidate and search ledger before asking the protected authority for fresh confirmation. Keep descriptive statistics and asymptotic arguments separate in the report.

The rejected shortcut is a competition-shaped wrapper returning `scores.csv`. It would reuse more DS code but preserve editable score authority, scalar optimization, and test-answer handling that conflict with the experiment. The rejected larger alternative is replacing Bigbrane's exercised instrument with RD-Agent's default evaluation stack. Retaining the instrument avoids unnecessary loss of its oracle/statistical/provenance contracts.

### Adapter B: DeerFlow scientific controller, alternative

Use approximately **five to seven cohesive modules**, plus the same protected service boundary and tests. This adapter can connect to fewer framework-specific research classes, but it must implement more of the scientific state machine itself.

1. Embed `create_deerflow_agent` with explicit model, supplied tools, full-state persistence, and `RuntimeFeatures`; use `SubagentConfig` for literature, design, candidate coding and interpretation roles. Do not use a full middleware takeover unless the required controls are re-established and tested.
2. Build trusted tools such as `register_hypothesis`, `register_protocol`, `run_development`, `read_development_receipt`, and `request_freeze`. A code-writing role receives candidate storage only. Neither generic bash nor a confirmation-data mount belongs in an analyst's tool set.
3. Implement a durable research state machine: proposed, designed, implemented, development-running, analyzed, rejected/inconclusive/selected, frozen, confirmed. Record experiment parentage and explicit stop/selection reasons outside conversational memory.
4. Use a started caller-owned `SubagentRuntime` and opt-in durable batches for independent work. Bind item keys to trusted idempotent attempt IDs. Batch completion/acceptance does not advance a scientific status without a validated receipt.
5. Attach `TaskLifecycleContributor`, `MiddlewareContributor`, and `SystemModelCallObserver` through the extension seams when the Gateway is used, or equivalent embedded middleware/ledger calls for a smaller headless integration. Retain raw prompts, source passages, tool outputs and immutable artifact digests; store long outputs outside bounded message previews.
6. Configure Docker AIO execution with pinned image, restricted egress and minimal mounts, explicit token/concurrency/command limits, and study-wide budget reservations. Keep the independent evaluator and its credentials outside this runtime.
7. Keep scientific planning and interpretation distinct from deterministic tests/statistics. Use Bigbrane's protected metric service for comparison and a separate derivation/proof review process for mathematical claims.

This option earns its cost if durable delegation, human workbench interaction, and provider flexibility dominate near-term needs. Its larger scientific-policy gap is why it is second for the user's present objective. Adopting both platforms at once would add two orchestration models before either has passed the experiment boundary tests; a single bounded adapter is the simpler first trial.

## Test-first acceptance plan

Write these tests before implementing the adapters. The numerical harness's existing checks remain unchanged. Each proposed test exercises the platform boundary, rather than rerunning Experiment 1 for selection.

### Shared contract and unit tests

1. **Hypothesis/protocol schema:** reject a proposal missing assumptions, a falsifier, budget, metrics or replication unit. Distinguish an empirical prediction from an asymptotic claim requiring proof. Reject metric/threshold changes after freeze.
2. **Metric authority:** a candidate writes a fabricated `scores.csv`, edits its own tests, or reports a favorable number. The returned scientific receipt must still derive from trusted predictions/scoring, or mark the attempt invalid.
3. **Status semantics:** valid negative, valid inconclusive, execution failure, invalid probability output and budget exhaustion all remain distinct and recorded. Only a declared development selection rule changes ranking.
4. **Comparison/resource contract:** recompute known fixture outcomes with the correct generator replication unit, paired controls, descriptive intervals, full learning curves, parameter conventions and training-plus-validation access. Include failed and losing candidates; distinguish analytical cost from measured scaling.
5. **Budget ledger:** count rejected proposals, retrying LLM calls, embeddings/retrieval, tool time, failed fits and confirmation separately. Missing usage remains unknown. Study admission refuses new work when committed/reserved resources reach the limit.
6. **Idempotency:** submit the same attempt ID concurrently and after interruption. It yields one committed experimental result, while retaining each real process attempt and any unknown partial-work cost.

### Shared isolation and end-to-end integration tests

7. **Secret/authority separation:** adversarial candidate code attempts to read confirmation arrays, oracle matrices, grader source/keys, controller credentials, Docker socket and ancestor paths/symlinks. Access must fail under the actual OS/container deployment, not only tool-name filters.
8. **Execution controls:** exercise a hanging child process, memory pressure, spawned grandchildren, background survivor and network exfiltration attempt. Verify deadline, cleanup, resource/egress policy and explicit failure receipts. Do not equate a timed-out HTTP request with a killed computation.
9. **Freeze and confirmation:** select one candidate using development feedback, freeze all digests, then score fresh protected generators/data. Further search or source/protocol edits cannot receive the same final capability. Reusing final scores as search feedback must require a new labeled study.
10. **Reproducibility and artifact completeness:** repeat a development fixture in the selected CPU image, interrupt/resume it, and independently recompute saved metrics from raw outputs. Test nested JSON/NPZ/PT artifacts, environment identity and all attempted hypotheses, including rejected branches.
11. **Deployment/provider smoke:** on the actual Apple Silicon host and selected Linux executor, verify image architecture, imports, daemon reachability, disabled GPU path, one-thread controls and effective network policy. Exercise JSON/schema/tool calls and streaming usage with each chosen hosted/local role model. Record the actual resolved provider/model and image digest.

### RD-Agent-specific acceptance tests

12. Construct the custom `Scenario`/`ExpGen`/`Developer`/feedback loop without Kaggle data or Qlib feature initialization. Assert the metaclass's stage order and use private helpers so unintended public methods do not become workflow steps.
13. Prove neither `TestEval.valid` nor `TestEval.eval` is invoked by the adapter; no reference answers or grader are ever injected into candidate storage. Test both successful and failing submission-format checks through the trusted service.
14. Save/load a signed snapshot after each stage, reject modified/unsigned snapshots, keep signing keys unavailable to candidates, and resume into a new checkout path without truncating earlier evidence. Test active-trace reset without losing earlier attempts.
15. Check logger-tag role routing and overlapping tags. If RAG is enabled, test its actual MCP service and Pydantic-AI provider mapping separately from the ordinary LiteLLM completion path. Validate that a native Anthropic setting does not silently become an unsupported RAG deployment.
16. Disable or replace archive cleanup, then verify all nested checkpoints and raw arrays survive. Exercise configurable workspace checkpoint size rather than relying on the stale 100 KB comment. Ensure stop/time limits cannot be enlarged by the candidate.

### DeerFlow-specific acceptance tests

17. Start the explicit persistent runtime, submit batches, terminate the worker, recover expired leases, cancel during tool assembly and retry under capacity pressure. Prove side-effect idempotency comes from the trusted attempt service, not the item-key prompt.
18. Assert that executor `completed`, batch `succeeded`, advisory acceptance and scientific confirmation are independent. UNVERIFIED or checker errors cannot promote a scientific result.
19. Verify same-run continuations share token usage, later runs get a new budget, retroactive child usage is counted, missing usage is flagged, and auxiliary calls/batch results enter the study ledger. Test bounded concurrent overshoot rather than assume a pre-call dollar cap.
20. Under the selected Docker runtime, check capability/user/seccomp/resource/egress settings and receipt binding. Reject candidate-authored fake test output and preserve external artifact digests independently of message compaction or short receipt hashes.

A bounded trial should report independently confirmed findings, valid negative results, protocol violations, full attempt counts, duplicate work, intervention count and total known/unknown resources. Adopt RD-Agent after these tests show that its abstractions reduce research-driver work without weakening the protected instrument. If adapting its domain assumptions consumes more work than the useful loop machinery saves, DeerFlow remains the alternate workbench foundation. No such trial has been executed here.
