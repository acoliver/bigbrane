VALIDATION GATES ADDED TO THE INSTRUCTIONS ABOVE (the host and the validation job enforce them; a task that fails any of them is sent back once and then dropped):

1. Claim polarity. A rule that decides a falsifier claim (falsifier.N) must have if_met "refuted" and must state the falsifier's own falsifying observation, quoted from that falsifier's own text, with the falsifier's own threshold. Do not attach a falsifier claim to a capability sentence, and do not mix falsifier claims and other claims in one rule. Write separate rules.
2. Quotes are claim-scoped. Each rule's quote must be text of every claim the rule names, not of some other claim.
3. Thresholds come from the quote. Every condition value must be a number that appears in the rule's quote, and every group a condition names (for example K=16) must be covered by the quote (a number in it, or a bound such as "K <= 48"). Do not subtract the uniform or unigram reference from a condition: the card states absolute thresholds. A retry may not change a threshold, operator, quote or claim list of a rule that was not named in the failure.
4. Positive control. A rule that can support the card from a low score needs "control_rule": the index of another rule of the same task. That is a rule with if_met "supported" whose conditions all ask the candidate alone for performance above a bar, for example the card's accuracy at small K. If the candidate does not meet the control rule, the rule is inconclusive. Rules that need a control: a "supported" rule with a limit condition (accuracy at most x, KL at least x), and a "refuted" rule whose conditions all ask for performance (its non-observation reads as the card surviving).
5. Training covers every test group. For every group, the longest training sequence must be at least as long as the longest test prefix of that group plus its answer, so train on episodes from every group. If a group's size cannot be trained within the caps, test it with a smaller size and list the change in deviations, or list the claim in untestable. Training sequences must also not be longer than the candidate's train_max_len when the user message states it.
6. The trained check compares the candidate with the better of the uniform and unigram references. A task that no model can learn in the given budget decides nothing, so size the training set and episode length to what the budget can learn.
7. Protocol parameters. Return "protocol_params": a list of {"name", "card", "task", "model_side"} for each size the card's claim text states as "name = value" (for example d = 64, V_c = 1024, trials = 500). "card" is the value in the claim text, "task" is the value your task uses, "model_side" is true for sizes of the model itself (d, M) and false for sizes of the data. Each "card" value must appear as "name = value" in a claim your rules name. Every parameter where task differs from card must be mentioned by name in "deviations". For a model-side parameter, the bench marks every rule of the task inconclusive when the candidate's describe()["hyper"] reports a different value than "task". Use an empty list if the claims state no such sizes.
8. Leak controls. The validation job scores recency (the j-th last prefix token), n-gram (last 1 or 2 tokens) and lookup (the token after the most recent earlier occurrence of the last prefix token) predictors. A condition asking the candidate alone for accuracy above a bar must not be met by a recency or n-gram predictor. If the answer is determined by an earlier occurrence of the last prefix token (key-value recall), set "solvable_by": "lookup"; the job then requires lookup to score at least 0.99 in every group.
9. Reference mechanism (optional, for tasks whose rules decide capacity claims). Return "reference": {"kind": "pair_memory", "d": <the card's d>, "min_token": <int>}. The validation job then scores the card's own d x d least-squares pair memory on your test prefixes: it stores the adjacent token pairs (x[t-1], x[t]) of each prefix without its last token, keeping only pairs where both tokens are at least min_token (set it just above your separator and marker tokens), reads out with the last prefix token and decodes with a tied random lift. Gates from its accuracy: a rule with if_met "refuted" must not be met by it; a limit rule (supported, with a condition such as accuracy at most x) must be met by it, otherwise the rule would refute a correct implementation of the card; a rule you name as a control_rule must be met by it. Rules with kl conditions or conditions that name another entrant are not checked this way. The reference's d must be listed in protocol_params as d with the card's value.
