WHERE A PREMISE IS SETTLED. Give every premise a `subject`:

- `frozen_definitions`: a claim about the card's own code, equations or frozen definitions, for example that the cost reference executes the card's equations with a definition's product spellings and retained buffers, or that a witness keeps the buffers a definition names. These are settled at stage M only. The host treats any premise whose text or measurement plan names one of your definitions (D1, D2, ...) as this subject, whatever label it carries.
- `mechanism`: a capacity or component the mechanism relies on (an oracle, a store, a prior). Stage C runs the magic-X test on it.
- `world`: external data, hardware, or a published result. Its measurement plan may be scheduled by test design, or its citation verified at stage C.

A `frozen_definitions` premise needs an obligation with `claim_id` null and `discharges` naming it, whose statement checks it and is frozen and run with the other statements. Calibration runs only stages M and C, so a measurement plan "for test design" would never run. Without such an obligation the host refuses the premise at freeze, and every claim that uses it stays unproven. Do not list the premise in the discharging obligation's own `premises`, and do not let a profile slot discharge it: a count check is not a check of the equations.

For the cost reference, write a `conformance` statement: `reference` (the id of the P1 cost statement, such as "O4.a"), `equations` (Python source defining `expected(params, sizes, tokens)` that computes the card's update and readout directly from your definitions with plain NumPy `np`, reading the parameters by the names a definition fixes, and returns one `{"state": ..., "output": ...}` per token: every array and number the definitions say is retained after that token, and what predict returns), and `streams` (from "repeated", "distinct", "random"). Leave `points`, `tolerance` and `precision_bits` out: the host sets them (FIX-20), the points from the protocol (every combination of the cost grid over the cost statement's sizes, at n = 256), the tolerance exact (0), and `precision_bits` from the card's resources.architecture.precision_bits; a statement that gives other values is refused. Both sides run at that one precision: the reference's counter makes every float at it, and the `np` your `expected` sees makes new float arrays at it when no dtype is given, on parameters already at it. So write no dtype other than the card's precision (casts to it are allowed and change nothing), and compute the operations in the order the definitions fix (the cost-reference recipe for each product and sum), because the comparison is exact. The host runs the reference that held for P1 and your `expected` on the same parameters, and compares the retained state (arrays matched one to one by shape and value, names and order ignored) and the output after every token. Name the parameter keys in a definition so the prover's reference exposes them.

If the frozen statements already require everything the premise says, do not write the premise. If they only match counts, they do not show the equations are executed; keep the premise and discharge it as above.
