ANSWER FORMAT FOR COMPONENTS, FINDINGS AND CONSERVATION (FIX-4). These rules replace the `components`, `new_premises` and `conservation` instructions of the system prompt wherever the two differ; the schema has `findings` in place of `new_premises`.

COMPONENTS. List every component the card relies on, with `role`: "mechanism" for an ordinary part of the card's own architecture (its matrices, tables, hand-set weights, retrieval and update steps), "external" for something supplied from outside it (an oracle, a perfect index, a precomputed answer table, a prior or a parser the mechanism does not compute). Give `statement_id` and `function` when an executed check defines it, `premise_id` when it implements one of the original premises, a short `subject` naming the gap, and `magic_x` code when the component, given to a plain baseline, could carry the claimed advantage by itself. The host decides cost coverage, not you: a component defined in a cost statement, or in a P2 or P4 witness that held under the frozen architecture contract while P1 held under the same contract, is covered. A runnable mechanism component without covered cost becomes an accounting finding on P1; its executed result stands. A component named only in prose, or an external component without covered cost, becomes an open premise on the claims that use it. Do not list a component merely to restate that an executed result holds.

MEASUREMENT OBJECTS (FIX-21). Use `role` "measurement" for a definition that belongs to a test or bound and is never supplied to the model at inference or training: a P5 hypothesis class, a P2 task generator, an evaluation set, a protocol constant. Example: the restricted target-rule classes of P5's sample entries are frozen in the P5 conservation statement (each `hypothesis_class` with its definition and `log2_size`); they are what the information bound counts, not something the trained model receives, so they are a measurement object, not an external prior. For such a component give `statement_id` null, name the object in `name` or `subject` (for example "P5 hypothesis classes", "copy task generator"), and set `used_by` to the obligations of the statements that define it. The host checks the role on structure: a measurement object is settled by the frozen statement that defines it, only when that statement held, and never becomes a premise; if that statement did not hold it stays open and the claim rests on that statement. The host corrects the role either way and records why: an external or prior component that is one of these objects becomes a measurement object, and a component labelled measurement that any mechanism, cost, conformance or learnability obligation uses, or that a witness defines in code, is settled as external. Anything the model is given at inference or training (an oracle, an index, a precomputed table, a prior built into its parameters) is never a measurement object.

FINDINGS. A finding is a dependency or a violation the results do not show. Each one needs:
- `subject`: a short name of the gap (for example "nesting decoder width", "hypothesis class size"); the same subject against the same claims is the same finding, so reuse it rather than writing two versions;
- `kind`: "missing_assumption" (a claim relies on something no check establishes), "witness_violation" (a submitted witness breaks the frozen statement, its definitions or the architecture contract), "accounting" (a cost P1 does not count), "explanation" (the card's account of how it works is wrong although the executed result holds; this attaches only to the card's own capability claims, never to a profile slot);
- `claim`: the dependency or violation in one sentence;
- `evidence`: an exact quote with its source: "card", "check" (the `text` of an M check, named by statement id), "definition" or "statement" (a frozen definition or statement, by id). A quote that is not exact text makes the finding unsupported;
- `dependency`: why the named obligations' conclusions need it;
- `used_by`: the obligations it affects;
- how it is settled, `testable_by`:
  - "code": `code` is Python defining `verify(witness)` that returns `(confirmed, evidence)`, `confirmed` True when the fact the finding rests on holds. `witness.sources` maps statement ids to the prover's sources, `witness.specs` to {"form", "spec"}, `witness.load(statement_id)` returns a source's module data and functions as the checks load them, `witness.layout(task, size, params)` and `witness.generate(task, size, count, seed, params)` are the task harness, `witness.survey(value)` lists every array reachable from a value with its shape. No imports, no names starting with an underscore, no eval, getattr or open. A finding that says code and gives none, or whose code does not run, is unsupported and blocks nothing;
  - "derivation": `derivation` is a SymPy relation {"symbols", "lhs", "rhs", "relation", "conditions"} that holds exactly when the finding is right;
  - "citation": `citation` and `record_quote`, a sentence of the source's title or abstract;
- `measurement_plan` when the dependency is real but can only be settled later by a measurement; `magic_x` when the dependency, given to a plain baseline, could carry the advantage alone;
- `targets` (FIX-13; empty unless `kind` is "witness_violation"): one entry per affected witness, {"statement_id": the executed statement whose source deviates, "deviation": the exact deviating text of that source, "edits": [{"anchor": exact text of that source, "replacement": its conforming text}], "why": why the edited source is the witness the frozen definitions ask for}. Name every affected witness separately, also when several share one deviation. The edit must remove the deviation and change nothing else: each anchor appears once in the source and stays on the lines that hold the deviation, and a replacement adds no number its anchor lacks, no name the source does not use, and no change of dtype or precision. The one exception is a precision edit (below), which is the conforming edit for a precision deviation. Weights, scales, sizes, counts, seeds, thresholds and the architecture contract stay as frozen. Give `edits` empty only when no narrow conforming edit exists, and say why. A precision deviation always has one.

The host runs every verification. Confirmed missing assumptions become open premises and block the claims they name until settled; findings that are not confirmed are recorded and block nothing. Findings that cannot be settled by code, a derivation or a citation are not findings.

MATERIALITY OF A WITNESS VIOLATION (FIX-13). Your `verify` code establishes that the deviation exists; it does not decide the claim, and it must not compute the claim's accuracy itself. For each target the host applies your edit to the recorded source, checks that the edit is narrow, and runs the edited source through the statement's own frozen check (for a construction, the same audited construction run, with the frozen spec, sizes, count, seed, precision and architecture contract). If the conforming source holds, the deviation is immaterial and the claim keeps its evidence. If it fails the frozen check (below the threshold, or a resource or numerical violation such as an overflow to NaN), the violation is material and the claim fails. If no target names a witness, your edit is not narrow, or the check does not finish, the finding is unresolved: it blocks the claim without counting as a measured failure. A finding about several witnesses is settled for each one separately.

PRECISION DEVIATIONS (FIX-15). When a witness computes at a precision other than the frozen numerical contract's (for example `.astype(np.float64)` in update or predict while the contract and `architecture.precision_bits` say binary32), the conforming edit restores the frozen precision, and you are expected to give it. A precision edit changes dtype casts and dtype arguments only, and only toward the frozen precision: `.astype(np.float64)` becomes `.astype(np.float32)` or is removed when the operand is already float32; `dtype=np.float64` becomes `dtype=np.float32`; an array constructor gets `dtype=np.float32`; a value is wrapped in `np.float32(...)`. Nothing else may change: no weight, number, name, operation or line structure. A precision edit may reach any line of the source, so restore every cast the update and predict functions use, not only the quoted one; one edit whose anchor is the whole body of those functions is fine. Do not mix a precision edit with any other change in one target, and do not move to a precision other than the frozen one (float16 or longdouble under a binary32 contract is refused). The host checks this by comparing the edited source with the original once dtype casts are removed from both, then replays it under the frozen check at the frozen precision.

Read the frozen definitions with their scope. A definition binds only the obligations that cite it, and a definition with scope cost_reference fixes the operation sequence of the P1 cost reference only: a P2 or P4 witness that evaluates the equations differently does not violate it. When the frozen numerical contract allows exact identities (a common score shift before exponentiating, log-sum-exp), using one is not a deviation. When the frozen precision or evaluation order excludes such a shortcut, it is a deviation, and the replay without it decides: agreement in exact arithmetic does not excuse an overflow.

CONSERVATION. `quotes` is a list of {"source": "card", "definition" or "statement", "ref": the definition or statement id (null for the card), "text": exact text}. Every number in `claims` other than 0 and 1 must appear in a quote, or be the `value` of an entry of `derivations`: {"value", "expression" (a formula with + - * / **, ceiling, floor, log, sqrt), "inputs" (names to numbers)} whose numbers and inputs all appear in quotes. For example a state of 32 bits per word times a frozen state-words formula at L = 64 is a derivation quoting the precision definition and the frozen statement.
